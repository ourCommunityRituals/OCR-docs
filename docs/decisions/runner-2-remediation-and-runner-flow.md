## Runner-2 remediation (fixes BOTH failure modes)
TWO independent bugs, fixed at the layer each lives in, shippable in stages.

FAILURE MODE 2 — semgrep exit 127 (workflow layer, SAME-HOUR unblock, ships first, independent of all fleet work):
Root cause confirmed: oursharedevents-ci.yml S0 (line 216-217) runs `python -m pip install semgrep` then the BARE console-script `semgrep scan`; S2 (line 1522-1523) uses `python3 -m pip install` then bare `semgrep scan`. pip drops semgrep.exe into a Python Scripts dir that provision-runner.ps1's canonical .env PATH deliberately omits (Git-Bash-first, no Python Scripts), so on BLOODRAVEN-2 bare `semgrep` = shell 'command not found' = exit 127; runner-3 only passes on a stale/divergent PATH. Proof-of-pattern: detect-secrets at line 235 already uses `python -m detect_secrets` and never 127s.
Fix, applied SYMMETRICALLY to S0 and S2:
1. Replace bare `semgrep scan ...` with module form `python -m semgrep scan ...` (resolves via interpreter site-packages, PATH-independent — the single load-bearing change).
2. Normalize the interpreter: use `python` in BOTH pip-install AND run for S0 and S2 (kill the S0 python / S2 python3 split so install-site == run-site).
3. Pin the version: `python -m pip install 'semgrep==<PIN>' --quiet` (no floating install; enables staged org bumps).
4. Loud pre-flight BEFORE the scan: `python -m semgrep --version || { echo '::error::semgrep unavailable on runner'; exit 1; }` — tool-unavailability fails traceable (#24), never 127-as-noise, never swallowed green.
5. Keep ALL --config flags and --error (real findings still fail — security not weakened). Keep the `|| SEMGREP_EXIT=$?` / `exit ${SEMGREP_EXIT:-0}` wrapper.
This cures the deterministic 127 immediately and independently; it does NOT require any runner env change (do NOT add a Python Scripts dir ahead of Git Bash — that would regress invariant #11).

FAILURE MODE 1 — no-log hang (fleet layer, staged behind the semgrep hotfix):
Root cause confirmed at watchdog.ts:73-79: the online branch scores any online runner healthy (busy or not), resets restartAttempts=0, and continues — no busy-duration check. A job in_progress ~30min with the runner online+busy is scored healthy every 60s tick and never recovered. ErrorCode.JOB_STUCK/QUEUE_TIMEOUT (errors.ts:16-17) are defined but dead and not in RECOVERABLE.
Remediation = SINGLE OWNER per runner + targeted recovery:
- BLOODRAVEN-2 and -3 both set hangOwner:'janitor' (grafted from C3): the invariant-#12 janitor (tools/runner/janitor.ps1, 1-min probe, per-workflow dwell caps S0=15m/T0=10m/T4=60m/default=15m) is the ONE actor that kills a wedged online+busy Worker. The concrete runner-2 repair is to re-run setup-runner.ps1 so runner-2 regains the janitor + probe scheduled tasks it lost via the out-of-band reconfig-bloodraven2.ps1 (which launched run.cmd directly). VERIFY the live scheduled-task inventory on runner-2 first; capture a real 30-min-hang _Worker/_Diag to confirm it presents as a Worker-over-dwell (not a Listener broker stall) BEFORE relying on the janitor path.
- The fleet's watchdog NO-OPS the hang path on janitor-owned runners — no split-brain, no PR-#159 double-bounce. It still owns offline recovery, provisioning-on-recovery, and force-kill for those runners.
- The fleet ALSO gains a real busy-dwell detector (wiring the dead JOB_STUCK), but it is armed ONLY for hangOwner:'fleet' hosts (janitor-incapable boxes), delivered as a lean, tested, but off-by-default path — not dead code, gated by config and covered by a pure-logic test, defended by corroboration (>=2 sustained ticks) + a 3-bounce/60min circuit breaker.

Deterministic env on recovery (defense-in-depth, closes the re-hang loop C1 alone left open): make watchdog.recover() re-register path fail-closed — after config.cmd and BEFORE startService, shell out (via execFile arg-array) to tools/runner/provision-runner.ps1 then verify-runner-env.ps1 (exit 0/1/2/3); if verify != 0, emit a new PROVISION_FAILED and DO NOT startService (a mis-PATHed runner-2 can never return online). This delegation satisfies invariants #11/#13 (canonical enforcement stays co-located, not in TS or loose root scripts).

## Optimized runner flow
END-TO-END STEADY STATE (easy to reason about — one owner per concern):

1. SECURITY BRACKET (one source, no drift). ADR-005 composite action .github/actions/security-scan/ owns: actions/setup-python@v7 + `python -m pip install 'semgrep==<PIN>'` + version pre-flight + `python -m semgrep scan --config=... --error --json-output=...`. Wrapped in reusable security-bracket.yml (workflow_call), consumed by every spoke at pinned @v1. S0 (job `security`, no needs) runs FIRST; S2 (job `security-post`, needs gate+staging, if always()) runs LAST. Both call the SAME composite, so the flow-bracket is uniform by construction and a single pinned bump updates both. Tool-unavailability fails loud; genuine findings fail via --error; a tooling crash is warn-and-continue mirroring the existing gitleaks exit-1-vs-other discrimination.

2. RUNNER FLEET (@ocr/runner-fleet = policy/orchestration brain; tools/runner/*.ps1 = host mutation). Each tick: gh.listRunners() (scope-aware: /orgs/{org} for BLOODRAVEN-2, /repos/{o}/{r} for BLOODRAVEN-3). For each runner:
   - online+idle → healthy, reset restartAttempts.
   - online+busy → healthy IF hangOwner=janitor (janitor owns the dwell kill). IF hangOwner=fleet → track busySince on the busy edge, compare elapsed to per-workflow dwell cap; on >=2-tick corroborated breach emit JOB_STUCK + run_cancelled, gh.cancelRun(runId), escalate to a force-kill bounce only if still wedged; 3 bounces/60min → STOP + RUNNER_POOL_DEGRADED.
   - offline/absent → recover(): stopService (Stop-ScheduledTask → PID-exit poll → scoped force-kill of Listener/Worker filtered by process path) → on re-register, config.cmd → provision-runner.ps1 → verify-runner-env.ps1 (fail-closed: PROVISION_FAILED if verify!=0, no start) → startService.

3. HANG DEFENSE OWNERSHIP is declarative and single: janitor for both production runners; fleet detector armed only where no janitor can run. The two never both act on the same wedge.

4. AUDIT. Every automated action (run_cancelled, hang_detected, restart, re_register, provision_failed, circuit_breaker_tripped) emits a typed WatchdogEvent correlated to the GitHub run/job id, written to a durable append-only JSONL sink mirroring the janitor's six signals, schema-gated to carry IDs + gate outcomes ONLY (no PII/IP/timestamp — audit the operators, never the attendees). In-memory ring retained for the dashboard.

5. SECRETS. PAT sourced from process.env.RUNNER_FLEET_PAT (never the plaintext fleet.config.json field); registration token fed to config.cmd via an ACL'd token-file (--token @file where supported) or stdin, not a CLI arg; all shell-outs use execFile arg-arrays (no string interpolation).

6. ROLLOUT. Everything shared (composite @v1, fleet provisioning + hang detector) is pinned-tag versioned and promoted BLOODRAVEN-3-first → soak → BLOODRAVEN-2 → org-wide, so a bad shared change reddens one spoke, not every spoke.

## Semgrep sub-service
Shape = ADR-005 composite action .github/actions/security-scan/ wrapped in reusable security-bracket.yml (workflow_call), consumed by spokes at pinned @v1. Composite steps: (1) actions/setup-python@v7 (python-version 3.11); (2) `python -m pip install 'semgrep==<PIN>' --quiet` (pinned, one interpreter); (3) pre-flight `python -m semgrep --version || { echo '::error::semgrep unavailable on runner'; exit 1; }`; (4) `python -m semgrep scan --config=p/nodejs --config=p/owasp-top-ten --config=p/r2c-security-audit --error --exclude=... --json-output=<out>.json || SEMGREP_EXIT=$?` then jq summary then `exit ${SEMGREP_EXIT:-0}`. Inputs: json-output filename (semgrep-results.json for S0, semgrep-post.json for S2) and any per-bracket config overrides. The reusable workflow exposes an S0 entry (called by job `security`, no needs) and an S2 entry (called by job `security-post`, needs gate+staging, if always()) so S0-first/S2-last stays uniform by construction. This collapses the two hand-wired copies (S0 lines 214-230, S2 lines 1519-1536) into one anti-drift source; a semgrep version bump is a single staged @v1→@v1.x tag. Resolution is via interpreter site-packages (PATH-independent), so it works on BLOODRAVEN-2's canonical Git-Bash-first .env with no Python Scripts dir added (protects invariant #11). Optional hardening: pre-install the pinned semgrep into the runner image so the composite asserts-and-uses (skip per-run pip), removing both the per-run cost and any residual PATH dependence.

## Open risks

- Fleet-to-tools/runner delegation couples the TS package to those scripts' exit-code contract (0/1/2/3) and Windows path layout; pin/verify the script interface with a smoke test and ensure non-Windows paths degrade gracefully rather than throw.

- Composite @v1 org rollout is org-wide blast radius; a bad tag reddens every spoke's S0+S2 at once — mandatory staged canary + pinned tag, never float, plus a governed semgrep pin-bump cadence so security coverage does not rot.
